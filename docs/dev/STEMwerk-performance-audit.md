# STEMwerk REAPER Pipeline and GPU Scheduling Audit

Date: 2026-05-13

Scope: audit only. No behavior changes are proposed here for UI, import/output behavior, quick toolbar actions, support bundles, or the Python backend.

## 1. Current Pipeline Overview

Current path:

1. REAPER/Lua reads the current item, track, and time-selection state in `scripts/reaper/STEMwerk.lua`.
2. `runSeparationWorkflow()` captures selection state, audibility/solo state, selected stems, output mode, model, device, and temp paths.
3. For multi-item or multi-track work, `_sep.buildSourceItemPlan()` creates a source-item plan sorted by source track index, item position, and original selection order.
4. `_sep.runSingleTrackSeparation()` creates a unique temp run directory and one job directory per planned job, such as `.../STEMwerk_<time>_<counter>/item_1` or `track_1`.
5. Each job gets an `input.wav` generated by Lua before Python workers are launched.
6. `_sep.startSeparationProcessForJob()` launches one Python worker per job in parallel mode, or one at a time in sequential mode.
7. Python runs `scripts/reaper/audio_separator_process.py input.wav output_dir --model <model> --device <device>`.
8. The Python wrapper constructs `StemSeparator`, selects a device, loads/uses `audio-separator`, writes stem WAVs into the job output directory, renames them to simple names such as `vocals.wav`, and writes progress/done markers.
9. Lua polls each job's `stdout.txt` for `PROGRESS:<percent>:<stage>` and `done.txt` for completion.
10. Once all jobs are done, `_sep.processAllStemsResult()` finds stem WAVs, optionally moves them to the project/custom stem-file destination, and imports them into REAPER via `PCM_Source_CreateFromFile` on new media items or via in-place take replacement.

## 2. Current File-vs-Memory Answer

STEMwerk is file-oriented today.

- Input audio is written to `input.wav` per job.
- Backend outputs are WAV files per stem, normally in each job temp directory as `vocals.wav`, `drums.wav`, `bass.wav`, `other.wav`, and optionally `guitar.wav`/`piano.wav`.
- Runtime/progress files live next to each job: `stdout.txt`, `separation_log.txt`, `done.txt`, `pid.txt`, and `exit_code.txt`.
- Temp roots are created under `getTempDir()` with names like `STEMwerk_<timestamp>_<ms>_<counter>`.
- If `Stem files` is `Project` or `Custom`, `HELPERS.finalizeStemFiles()` moves generated stem WAVs to that target directory before import.
- No audio is passed by shared memory, pipe, or in-process buffer between REAPER and Python.

Extraction details:

- Lua primarily extracts source audio with `ffmpeg`, using `-ss`, `-t`, `-ar 44100`, and `-ac 2`.
- Lua falls back to REAPER `CreateTakeAudioAccessor`/`GetAudioAccessorSamples` and writes its own 32-bit float WAV when ffmpeg fails or when a default-playback partial slice should preserve split/arrangement context.
- The AudioAccessor path is called from the Lua/REAPER workflow before backend worker launch, so it remains on the REAPER side and should be treated as main-thread-sensitive.
- REAPER import remains file-based: stem paths are loaded with `reaper.PCM_Source_CreateFromFile(...)`, then attached to newly created media-item takes.

Changing to a memory pipeline would require a new IPC contract, a new backend input reader, careful lifetime/error handling, and still would not remove file-oriented REAPER import unless import is redesigned separately.

## 3. Current Concurrency Model

The current multi-job model is process-per-job.

- Each source job has its own temp directory and its own `input.wav`.
- In parallel mode, `_sep.runSingleTrackSeparation()` starts all jobs immediately.
- In sequential mode, it starts one job and starts the next only after `done.txt` appears.
- `SETTINGS.parallelProcessing` defaults to `true`.
- There is no numeric max worker count. Parallel effectively means `number of jobs`.
- There is no GPU queue, GPU semaphore, file lock, or per-device concurrency limit.
- DirectML multi-job runs are forced sequential when the requested device explicitly contains `directml`.
- Auto CPU-only runs can be forced sequential if runtime device discovery shows no GPU.
- CUDA, ROCm-as-CUDA, MPS, and auto-selected GPU runs can currently launch multiple GPU-heavy Python workers at once.

Model lifecycle:

- Each Python process imports `stemwerk_core`, creates a `StemSeparator`, and calls `sep.separate(...)` once.
- `stemwerk_core.separator` has an in-process `_SEPARATOR_CACHE`, but that cache does not cross process boundaries.
- With 8 selected clips in parallel mode, the expected behavior is 8 job directories, 8 `input.wav` files, and up to 8 independent Python processes, each able to select the same GPU and load/use the model independently.
- Model files are cached on disk via `AUDIO_SEPARATOR_MODEL_DIR`, but model objects and CUDA/ROCm/MPS/DirectML contexts are not shared between Python processes.

## 4. Progress Percentage Behavior

Progress is partly real and partly synthetic.

- `audio_separator_process.py` emits `PROGRESS:<int>:<stage>` to `stdout.txt`.
- `StemSeparator.separate()` emits initialization/model-load progress from 0-10%.
- It emits 11% at `Starting separation`.
- During `separator.separate(str(input_path))`, a side thread estimates progress from 12-88% based on elapsed time and expected duration.
- After `separator.separate(...)` returns, it emits 92% `Writing stems`, then 100% `Complete`.

So a visible stall around 87% does not necessarily mean all jobs are waiting at the same real backend phase. It means each process is still inside `audio-separator`'s `separator.separate(...)`, and the local synthetic estimator has approached its 88% cap. The observed GPU ramp near that point could be real late GPU work inside `audio-separator`, delayed scheduling after model/setup/I/O, or simply a mismatch between the estimator and actual backend phases.

The current progress protocol does not expose model-load end, inference start/end, stem-write start/end inside `audio-separator`, GPU wait time, or per-process queueing.

## 5. Risk Analysis

Main risks:

- GPU VRAM pressure: parallel selected clips can create multiple independent Python processes and GPU contexts for the same model.
- Duplicated model loads: one in-process cache exists, but parallel jobs are separate processes, so the cache is not shared.
- CUDA/ROCm: multiple Torch processes can compete for the same `cuda:0` device; ROCm follows the CUDA-facing path in this code and has similar pressure risks.
- DirectML: explicit DirectML multi-job runs are already forced sequential, which suggests known instability or output-loss risk on that path.
- MPS: `auto` on Apple Silicon currently prefers CPU, but explicit MPS can still hit MPS-specific fallback/unsupported-op behavior.
- Disk I/O pressure: many jobs write temp `input.wav`, backend stem WAVs, stdout/log/done files, and possibly move final stems to project/custom paths.
- REAPER main-thread constraints: AudioAccessor extraction and item/track import should remain on the REAPER/Lua side; moving extraction off-thread would need a different source-audio strategy.
- Cancellation reliability: Lua kills known worker PIDs from `pid.txt`, but cancellation is best-effort and process trees/backends may still leave partial files.
- Crash recovery: the file-based temp/log/sentinel design is useful for recovery and debugging; memory-only designs would make failures harder to inspect.
- Support bundle usefulness: current artifacts (`stdout.txt`, `separation_log.txt`, `exit_code.txt`, run summaries, timing files) are valuable, but phase visibility is still too coarse for GPU contention analysis.

## 6. Optimization Options

Safest to riskiest:

### Option A - Instrument only

Add phase timing logs without changing behavior:

- `extract_start` / `extract_end`
- `python_launch`
- `model_load_start` / `model_load_end` if detectable
- `inference_start` / `inference_end` if detectable
- `stem_write_start` / `stem_write_end`
- `import_start` / `import_end`
- per-job wait time
- future GPU queue wait time

This is the safest first step because it can prove whether the 87% observation is a real backend phase boundary or a progress-estimator artifact.

### Option B - GPU concurrency limiter

Keep CPU/audio prep parallel, but limit GPU-heavy work to a conservative default of one process per GPU.

Possible variants:

- Lua scheduler launches fewer GPU jobs concurrently.
- Backend-side global file lock around GPU inference.
- Per-device limit setting, initially hidden/internal.
- Future explicit limit for CPU, CUDA/ROCm, DirectML, and MPS separately.

This is likely the best short-term performance-risk reduction. It preserves file-based extraction/import and avoids a large architecture change.

### Option C - Single long-lived backend worker

Run one Python daemon/worker that loads the model once and processes a queue.

Pros:

- Avoids repeated model load.
- Avoids multiple CUDA/ROCm/MPS/DirectML contexts for one STEMwerk run.
- Gives central scheduling and progress control.

Cons:

- More lifecycle complexity.
- Harder cancel/restart/crash recovery.
- Needs IPC/protocol design.
- More packaging and cross-platform risk.

### Option D - Batch multiple clips into one backend invocation

One Python process handles multiple input WAVs sequentially or in a batch.

Pros:

- Fewer process starts.
- Model can load once per batch.
- Simpler than a persistent daemon.

Cons:

- Progress, cancellation, partial failure, and import mapping become more complex.
- One failing batch can affect multiple jobs.
- Requires a new backend CLI/protocol.

### Option E - Memory/shared-memory pipeline

Avoid temp WAV inputs.

Pros:

- Less input disk I/O.

Cons:

- Much more complex with REAPER Lua and the main-thread AudioAccessor constraint.
- Harder crash recovery and support diagnostics.
- REAPER import remains file-oriented unless output import changes too.
- Not a good first optimization target.

## 7. Recommendation

Start with instrumentation plus a conservative GPU concurrency limiter prototype.

The next implementation should not attempt memory piping or a daemon first. The current performance concern is more consistent with process/model/GPU scheduling pressure than with the existence of temp WAV files. The file-based design also gives strong recovery and support-bundle value.

Recommended sequence:

1. Add backend phase markers to stdout/stderr and Lua timing files.
2. Add a hidden/internal GPU concurrency limiter for multi-job runs.
3. Compare default parallel, sequential, and limited-GPU runs on the same selected-clip set.
4. Only consider batching or a daemon after timing proves repeated model load and GPU context duplication dominate.
